# Decisions

- **Product name:** SettleCraft. Shared branding lives in `packages/shared/src/index.ts`; some UI copy explicitly uses the name.
- **Local modular monolith:** React/Vite, Express, PostgreSQL. No hosting or paid services. The original presentation is not attached; attribution to it is based solely on the provided brief. Its conceptual financial infrastructure, ledger, risk, queues and ML idea is preserved. React/Vite, auth details and module boundaries are implementation choices in the brief.
- **Typed SQL instead of an ORM:** `pg` with typed result contracts, parameterized SQL, checked-in migrations and explicit transaction helpers. SQL makes locking, deferred constraints and atomic operations visible. Database tests verify behavior; this is not a claim of compile-time SQL verification.
- **Ledger-derived balances:** No cached balance column. Credits minus debits on wallet liability accounts is authoritative. This avoids projection drift at portfolio scale; the tradeoff is aggregation cost. Reconciliation checks journal balance and negative wallets, not an imaginary cache.
- **Posting boundary:** Journals and entries are created in one transaction. A deferred trigger checks at least two entries and zero debit-credit sum. Entries can only be appended during their journal's creating transaction. Updates/deletes are rejected. A privileged DB owner can disable triggers; that is outside the local application trust boundary.
- **Concurrency:** Lock wallets in UUID order; query balances after obtaining the locks. Use transaction-scoped advisory locks for actor/scope/idempotency key. Risk history is evaluated while the sender is locked. Review decisions lock the transfer before wallets. No process-local money locks.
- **Pending review:** No reservation. Approval can become FAILED after a fresh funds/status check. The original API response stored under an idempotency key remains stable; GET transfer returns the current state.
- **Reversals:** Admin-only, full amount, once per completed transfer, recipient must still have funds. A new compensating journal preserves history. Partial refunds and user-initiated refund workflows are outside this baseline.
- **Funding:** New registrations get zero balance. Seeded Rahul/ Priya receive ₹2,000/₹1,000 via balanced issuance. User funding requests require admin approval, max ₹10,000 each and ₹20,000 rolling daily total including pending requests.
- **Rules first:** Scores sum and cap at 100, review at 60. No model training or fraud accuracy claims. Optional ML/Ollama and Redis/BullMQ are deferred; PostgreSQL is sufficient for the local outbox.
- **Event delivery:** Worker locks outbox rows FOR NO KEY UPDATE SKIP LOCKED, allowing receipt foreign-key checks. Delivery may happen multiple times; receipt ID uniqueness makes processing idempotent. Events never authorize or mutate money.
- **JWT sessions:** Access tokens stay in memory. Each request checks the associated non-revoked DB session and current user role/status. Refresh tokens are hashed, rotated, and family-revoked on replay. SameSite Strict cookie, exact Origin and custom header protect cookie writes.
- **Versions:** Node 22.21.1 met the official Vite requirements (https://vite.dev/guide/) and Express 5 requirements (https://expressjs.com/en/starter/installing/). Lockfile is authoritative. PostgreSQL 15.19 verified locally.
